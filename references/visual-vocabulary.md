# ゲームUIの視覚語彙

視覚語彙とは、プレイヤーが見たものをゲーム内の意味や操作に結びつける約束。**形・位置・まとまり・量・変化**を使う。同じゲームの別の場面でも、前に覚えた約束で判断できるようにする。

たとえば「光るところを押す」はその場の誘導。船とドックに同じしずくを置き、次に来た箱の船も同じ形のドックへ案内できれば、見方を教えたことになる。しずくが燃料なのか水なのかまで、絵だけで伝わるとは限らない。

## 1. プレイヤーが知りたいことから割り当てる

| 知りたいこと | 主な手がかり | 使い分け |
| --- | --- | --- |
| **何か**：燃料か部品か | シルエット・模様 | 資源の形を船、ドック、倉庫で使い回す。色は補助。残量や警告で資源の形自体を変えない。 |
| **どれと関係するか**：どの船とどのドックか | 近さ・同じ枠・短い接続線 | 同時に見る物を寄せる。離れていて分かりづらい時だけ線を引く。全候補に線を引きっぱなしにしない。 |
| **どれくらいか**：残り・差・次の節目 | 長さ・共通の基準線・目盛り | 比べるバーは始点と目盛りをそろえる。残り3秒や必要2個のように厳密な値は数字も出す。 |
| **今どの状態か**：空き・処理中・完了 | 定位置の輪郭・塗り・印 | 空枠→枠の内側が埋まる→出港の印。表示の場所は変えない。フォーカス枠は完了の印と分ける。 |
| **次に何ができるか**：押す・置く・戻す | 押せる面・受け口・結果の予告 | ドロップ先に置いた後の形を見せる。見た目がボタンなら押せる。鍵は未解禁、禁止印は今は置けないなど、原因を混同しない。 |
| **何がどこへ変わったか**：移送・獲得・消費 | 同じ物を追える短い移動＋結果の静止表示 | 資源が倉庫から船へ動き、出発元の数が減る。到着先の変化も残す。残り時間や失敗理由を一瞬の演出だけで済ませない。 |

「同じ形＝同じ種類」「枠＝押せる・選べる」のように、**同じ場所で競合する意味に同じ見た目を使わない**。役割の違う印は別の位置に置く。たとえば燃料の印はカードの左、処理状態は右。赤を燃料色に使うなら、不足は色の変化だけにせず、空枠と不足数でも出す。

実例：Factorioは、持っている物の枠と作成候補のボタンを見た目で分ける一方、同じ品の説明はレシピ・在庫・物流で揃えています。[Character GUI](https://factorio.com/blog/post/fff-289)・[New Tooltips](https://factorio.com/blog/post/fff-318)。**物の正体は揃え、操作の違いは揃えない。**

## 2. 覚え方も作る

1. **既知の約束を借りる。** 操作なら戻る矢印、開始なら再生の形など、届ける相手や機器で見慣れたものから考える。歯車の「設定」と工場の「歯車部品」が同じ場面に並ぶなら片方を変える。実物に似ていることと、押した結果まで分かることは別。
2. **初出は対象の横で意味を結ぶ。** 新しい印は、実物・短い名前・操作直後の変化を近くに置く。別ページの凡例だけに任せない。初回は一つの関係が見える場面にするが、「ここを押す」だけで進めない。
3. **次で使い回す。** 燃料で覚えた「同じ形のドックが速い」を、積み荷と修理でも使う。教える便だけの目立つ色や点滅は外して確認する。矢印を外した途端に迷うなら、関係の見え方を直す。
4. **速さ・可否・警告を区別する。** 「同じ印なら速い。他でも作業できる」場合は、同じ印を優先の手がかりに使い、ほかを禁止の見た目にはしない。選択前に何が得か、選択後に何が確定したかを別々に見せる。

## 3. 動きに任せるのは変化、静止で読めるのは状態

- 船がドックへ移る、鉱石が残高へ移る、残量が減る。**いま実際に変わった対象だけ**を動かす。同じ船の輪郭や名前は保ち、別の船へ変身させない。
- 原因と結果を同じ画面でつなぐ。たとえば資材消費→作業進捗→出港可能の順。成功と失敗に同じ派手な光を使わない。入力受理を即座に示し、本当に成功するまでは成功印を出さない。
- 動きを止めた1枚でも、何が完了して次に何をできるか分かるようにする。動きを減らす設定では、移動を省いて到着先のマークや数値を更新する。
- 地形やキャラの動きで読めるならHUDに重ねない。反対に、カメラの死角に隠れる・背景に埋もれる・細かい数値を比較するものは、定位置のHUDや短いラベルへ戻す。

## 4. 文字や別の手がかりを残す所

- **アイコンだけでは意味が割れる、初出、慣れない操作、取り返しがつかない操作**には短いラベルを添える。何を消すか、何個足りないか、押すと何が起きるかを省かない。「あと1個」「出港」には仕事がある。重複した説明文を先に消す。
- 重要な意味を色、点滅、音のどれかに任せきらない。形・模様・位置・短い語を組み合わせ、対応環境ではボタンに読み上げ名を付ける。必要に応じて音・音声・振動を選べるようにする。装飾の絵と、操作の手がかりを区別する。
- 白黒テストで色だけの区別を見つける。ただし、白黒で見えることを色覚多様性や低視力への対応の証明にしない。最小サイズ・明暗の異なる背景・無音・動き軽減でも確認する。ホバーだけで必須情報を出さない。

## 実装前の小さな凡例

意味ごとに下の1行を書く。迷ったら、実装より先に既存画面と照らす。同じ部品（SVG、描画関数、UIシーンなど）を参照し、別画面で形を手描きし直さない。

| 意味 | 固定する形と場所 | 状態が変わるもの | 文字・代替 |
| --- | --- | --- | --- |
| 燃料 | 船の要求・ドックの設備・倉庫に同じしずく | 支給時はしずくが同じ形のまま移り、在庫の数が減る | 初出「燃料」。足りなければ「あと1個」 |
| 作業中→出港可 | ドック右上に同じ枠 | 進み具合を枠内で表示し、完了時は出口向きの矢印 | 押せるようになったら「出港」。動きなしでも状態は残る |
| 置けない床 | 置こうとしている物の真下 | 斜線は衝突しているマスだけ。仮の配置と確定済みを区別 | 数や仕様が理由なら「電力不足」などを添える |

この表から確認する：燃料の印を見たら、船・ドック・倉庫で同じ物を探せるか。次に見る印はどれか。条件を満たしていないのに成功して見える箇所はないか。

もう一例：採掘ゲームで「燃料不足」「ブースト可能」「過熱」に同じ稲妻を使うと、色を見分けても意味は覚えにくい。燃料はタンク＋残量、ブーストは押せる二重矢印、過熱は温度計＋上限線に分ける。3種類を並べる必要がない場面では出さない。

## 見た目ではなく、判断をテストする

最初に「見える」「隣の印と見分けられる」「意味と押した結果が分かる」「別の場面でも使える」を切り分ける。印の意味があやしいときは単体で何に見えるかを先に聞き、別の初見プレイヤーには実際の画面を見せる。単体で名前を当てられなくても、画面内で操作を予測できる場合がある。

| 試すこと | 観察すること |
| --- | --- |
| 最初の船を、説明を読み上げずに渡す | 最初に押した物と、そこを選んだ理由。促さないと分からなかった箇所。 |
| 次に、別の印の船。ドックの並びや空き状況も変える | さっきの場所を覚えただけか、形と条件を見て判断できたか。 |
| 一度わざと不足させる | 何が足りず、どこで補い、どう戻るか。エラーだけ読めても復帰できなければ不十分。 |
| 動き軽減と狭い画面で繰り返す | 同じ判断ができるか。動きが終わった後や指で画面を隠した状態でも読めるか。 |

A/Bを作るなら船・ドック・得点・入力・難度は同じにし、比較対象だけ変える。見るのは誤タップ、最初の正しい操作までの時間、別の船への応用、復帰できたか。開発者が踏めた経路やコードのテストは、初見の人が理解した証拠にはしない。実際に見ていない場合は「初見での理解は未確認」と書く。

## 参考

文中のゲームUI手順は、以下を踏まえたこのスキルの実装方針。各研究がゲーム内の効果を直接測ったという意味ではない。

- [Jacques Bertin: Semiology of Graphics 抜粋](https://www.esri.com/content/dam/esrisites/en-us/esri-press/pdfs/semiology-graphics-diagrams-networks-maps-sample-chapter.pdf)：描画前に、共通する意味と変わる値を分ける。図表の分析法をゲームUIへ応用。
- [McDougallほか, 1999: Measuring symbol and icon characteristics](https://link.springer.com/article/10.3758/BF03200730)：239種の記号について、見慣れや具体性、絵と意味との距離などを分けて評価。特定のゲームでの成績を測った研究ではない。
- [ISO 9186-1 の公開概要](https://www.iso.org/standard/59226.html)：意図した意味が絵から読み取れるかを確かめ、難しければ対象の言語で文字を補う。上記の確認手順はISO準拠試験ではない。
- [Andersenほか, 2012: The Impact of Tutorials on Games of Varying Complexity](https://grail.cs.washington.edu/projects/game-abtesting/chi2012/)：3作品でチュートリアルによる継続・参加への効果が異なった。説明を増やせば理解度が上がるという根拠ではない。
- [Don Norman: Signifiers, not affordances](https://jnd.org/signifiers-not-affordances/)：できる操作と、何をすればよいかを知らせる知覚可能な印は分けて考える。設計論。
- [Heer & Bostock, 2010: Crowdsourcing Graphical Perception](https://idl.cs.washington.edu/files/2010-MTurk-CHI.pdf)：図表の量を比べる課題で共通尺度上の位置が有利だった。ゲームHUDすべての読みやすさや正解の表示形式を示すものではない。
- [Heer & Robertson, 2007: Animated Transitions in Statistical Data Graphics](https://idl.cs.washington.edu/files/2007-AnimatedTransitions-InfoVis.pdf)：同じ対象を追える遷移の利点と、対象の重なり・意図しない因果を感じさせる問題。統計図表の実験で、ゲームの最適速度は別途確認する。
- [Wube: Factorio Friday Facts #280](https://www.factorio.com/blog/post/fff-280)：経路を確定前にプレビューし、駅を使えない理由を駅のそばで示す実装例。
- [Valve: Illustrative Rendering in Team Fortress 2](https://cdn.fastly.steamstatic.com/apps/valve/2007/NPAR07_IllustrativeRenderingInTeamFortress2.pdf)：シルエットと装備でクラスを見分ける制作例。役割を伝える形は、アイコンだけでなくキャラクターにも使える。
- [W3C WCAG: Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)：色だけで情報を区別しない。ゲーム全体のアクセシビリティを保証する基準としては扱わない。
- [Sucker Punch: Crafting the world of Tsushima](https://blog.playstation.com/2020/07/09/crafting-the-world-of-tsushima/)：風の向きを植物・布・粒子の動きで伝える制作例。HUDを無条件に削る根拠ではない。
- [Xbox Accessibility Guidelines: 103 Audio and visual cues](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/103) ／ [114 UI context](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/114)：色に偏らない手がかり、操作対象とラベルの関係、視覚に頼れない場合の手がかり。
