# ゲームUX：初見から、次の一手まで

画面が読めても、毎回ウィンドウを開き直したり、考えている間に時間切れになったりすると遊びづらい。UIの見た目だけでなく、**気づく → 選ぶ → 操作する → 結果を見る → 次に動く**を一続きで見直す。

## 1. まず1プレイを通す

タイトルから、初めて小さな成果を出すまで。次に、同じ操作が3回続く場面と、一度ミスした場面を通す。各場面で「その時点で見える情報」「操作回数」「必須の画面切替」「操作できない待ち」「ミスの後にやり直す手数」を書く。途中からテストすると、開始時の迷いを取り逃す。

| 見る場所 | 確認すること |
| --- | --- |
| 初見 | 説明されずに何を押すか。最初の「できた」が、遊びの本体と同じか。 |
| 2回目 | 一度覚えた操作を、違う対象や位置でも使えるか。練習専用の誘導だけで進んでいないか。 |
| 繰り返し | 同じ選択をしているだけなのに、毎回別画面や確認を通っていないか。 |
| 妨げと復帰 | 誤タップ、資材不足、閉じる／戻る、回線待ちの後に、どの状態から再開するか。 |
| 手触り | 押したこと、処理中、確定を見分けられるか。演出中でも次にできる操作が分かるか。 |

## 2. 判断は残して、その前後の手間を減らす

- 結果が変わる選択は残す。資材1個で通常補給か、2個で急ぐかは攻略。何も選ばないのに同じドックを押し直し、同じ小窓を閉じるのは手間。**削る前に、何がゲームの判断かを書き出す。**
- よく使う安全な操作は対象のそばに。別の画面は詳細、比較、設定など、開く価値があるときに使う。既定値で何が起き、いくら消費するかは押す前に見えるようにする。危険・高コストな操作まで一律にワンタップにしない。
- 最初に一気に教えない。無得点・時間制限なしの一隻で、実際に接岸から出港まで通す。詳細は必要になったときだけ見せる。次の一隻では特別な誘導を外し、同じ操作を使えるか見る。慣れた人には練習を繰り返させない。
- ドラッグに意味がある場合も、移動・仕分けなら「対象を選ぶ → 行き先を押す」を用意できる。長押しを使う場合は、時間がかかる理由と進み具合を示し、可能なら押し続けなくていい代替を付ける。キー操作でもそこにたどり着けるか見る。

実例：Factorioでは、設計図を置く場所はプレイヤーが決めたまま、図面を手に持った状態でズレを見て調整できるようにしました。[制作記事](https://factorio.com/blog/post/fff-404)。消したのは配置の判断ではなく、設定画面を何度も開く手間です。

## 3. 待ちを分ける

- **遊びの待ち**：補給にかかる時間を見ながら、別の船をさばく。残りが分かり、待っている間も判断できる。
- **UIだけの待ち**：詳細画面を閉じる演出で毎回入力が止まる。繰り返しなら短くするか、入力を止めない。入力を受け付けた印はすぐ出すが、完了は本当に終わってから出す。
- 時計で競うなら、時間制限をなくせば解決とは限らない。むしろメニューが盤面を隠している間に時間が減る、初出の説明を読んでいる間に取り返しのつかない損が出る、などを先に取り除く。時間が進む画面と止まる画面を必要に応じて伝える。
- 待っているもの、残り時間、他にできることを近くに置く。分からない所要時間を偽の秒数や埋まるバーで見せない。

## 4. 詰まった場所から立て直せるようにする

- 不足は該当する資源名と数を、止まった選択のそばに出す。「失敗」だけで終わらず、補う・別の選択にする・戻るのどれができるか示す。
- 補給へ寄り道しても、対象と選んだ案を保ったまま元へ戻す。足りるようになっても勝手に確定しない。取消で何が保たれ、何が戻るかも揃える。
- 押し直し・連打・ダイアログを閉じる最中の操作で二重消費しない。閉じた後のフォーカスは元の操作へ。ドラッグが失敗したときは元の位置に戻し、消えたように見せない。

## 作例：ほしみなと管制局

- **通常の船**：船を選ぶ → ドックへ → その場で「補給 1」→ 出港。よく使う道を短くし、船の進捗は盤面に残す。
- **急ぐ船**：「優先」から消費・時間・得点の比較を開く。通常補給を省略して自動で払い込む必要はない。
- **資材不足**：同じドックの「あと1個」から該当資材へ。購入を確認し、同じ船・同じ作業に戻る。補給を別途確定する。通常と優先の選択を維持できる場合は維持する。

## 検証は「通れた」と「迷わなかった」を分ける

改修前後を同じ船・在庫・時間設定で比べる。初見の人には手順でなく目標だけ渡す（例：「船を一隻出港させてください」）。最初の妥当な操作までの時間、一隻目までの操作数・所要時間・立ち止まり、誤操作後に戻れたかを記録する。操作中に誘導した場合はその箇所も記録する。2回目は別の船、次は不足や取消を試す。両案を同じ人に見せると先に触れた経験が混ざるので、比較が必要なら順序を入れ替えるか初見の人を分ける。

自動・開発者テストで証明できるのは画面や操作の動作まで。少人数の観察はつまずきの発見に使い、理解率全体や継続率の改善を断定しない。未確認の端末・初見・入力方法は未確認と書く。

## 参考

- [Andersenほか：The Impact of Tutorials on Games of Varying Complexity](https://grail.cs.washington.edu/projects/game-abtesting/chi2012/)：3作品の実地比較で、チュートリアルによる継続・参加への効果が作品の複雑さによって異なった。短ければ常に良い、という結果ではない。
- [Xbox Accessibility Guidelines：115 Error messages and destructive actions](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/115)・[116 Time limits](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/116)：原因と修正手段、破壊的な操作の見直し、UIを読んで操作する時間。対戦や制限時間そのものを否定する指針ではない。
- [W3C：Making Content Usable](https://www.w3.org/TR/coga-usable/#help-users-avoid-mistakes-and-know-how-to-correct-them)：戻るときに入力を失わない、取り消しを簡単にする、操作を受け取ったことを伝える設計案。WCAG本文とは別の補足資料。
- [W3C：Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html)：ドラッグが本質でないときのポインター代替。キーボードを付けるだけで代替できたとは限らない。
- [GOV.UK Service Manual：Using moderated usability testing](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing)：操作の答えを含まない課題で、人がどこで詰まるか観察する手順。上のゲーム向け指標は応用案。
